# O Anti-Roadmap: Os Limites da NakeDev Framework

Este documento estabelece a nossa **Barreira de Fogo**. O maior erro ao desenvolver jogos é o "Feature Creep" (tentar construir todos os sistemas de uma vez). A NakeDev Framework foi desenhada para ser estritamente um motor de movimentação, combate e câmera (Core TPS). **Ela não é uma Engine completa.** 

Para garantir que a Framework seja leve, manutenível (KISS/YAGNI) e permita que você aplique o *Game Feel* exclusivo do seu próprio jogo, **A FRAMEWORK NUNCA DEVE FAZER AS SEGUINTES COISAS:**

---

## 🚫 1. Sistemas de UI (Canvas, HUD, Menus)
**A Framework NÃO PODE:**
- Instanciar ou referenciar `Canvas`, `Image`, `Text` ou `Slider`.
- Ter um script `UIManager.cs`.
- Tocar ou desenhar interfaces visuais de forma alguma.

**Por quê?**
A UI define grande parte do *Game Feel*. Um inventário em grid (Resident Evil) é totalmente diferente de um inventário em slots (The Last of Us). As cores, as fontes e os efeitos visuais são escolhas que pertencem exclusivamente ao seu projeto.

**Como funciona então?**
A Framework apenas **emite Eventos**.
- *Framework:* `public event Action<int, int> OnAmmoChanged;`
- *Seu Jogo:* Você cria um script (ex: `HUDManager.cs`) que escuta esse evento e atualiza o texto na tela de forma independente.

---

## 🚫 2. Sistemas de Inventário e Crafting
**A Framework NÃO PODE:**
- Ter listas de itens (`List<Item>`), calcular peso de mochila ou possuir lógicas de combinar itens (como erva verde com erva vermelha).
- Decidir como os itens são armazenados fisicamente.

**Por quê?**
Sistemas de inventário variam drasticamente dependendo do gênero do jogo. Criar um inventário genérico e acoplado na raiz do personagem resulta em um código complexo e difícil de expandir.

**Como funciona então?**
A Framework gerencia apenas o **Equipamento Ativo**. Ela sabe qual arma está nas mãos do jogador no momento (`CurrentWeapon`) e quanta munição está no pente daquela arma. A forma como a arma foi parar lá e como ela é armazenada na mochila é responsabilidade do seu sistema de inventário.

---

## 🚫 3. Sistemas de Save & Load
**A Framework NÃO PODE:**
- Ter um script `SaveManager.cs`.
- Escrever arquivos JSON, gerenciar PlayerPrefs ou comunicar com serviços em nuvem.

**Por quê?**
Os dados que precisam ser salvos variam absurdamente entre projetos. Um jogo pode salvar posições exatas, outro salva portas e baús abertos, enquanto outro rastreia escolhas narrativas complexas.

**Como funciona então?**
Você deve criar o próprio sistema de Save no seu jogo. Quando o jogador salvar a partida, seu sistema simplesmente lê as variáveis públicas fornecidas pela Framework (ex: `player.CurrentHealth`, `player.transform.position`) e as salva da maneira que preferir.

---

## 🚫 4. Gerenciamento de Áudio Global (Music/SFX Managers)
**A Framework NÃO PODE:**
- Ter um `SoundManager.cs` que controla as músicas de fundo do cenário.
- Tocar clipes de áudio no código de maneira engessada usando lógicas como `AudioSource.PlayClipAtPoint(clip)`.

**Por quê?**
Você pode querer utilizar o sistema de áudio nativo da Unity, middlewares como FMOD ou Wwise, ou implementar sistemas dinâmicos únicos para a sua atmosfera sonora.

**Como funciona então?**
A Framework expõe "Gatilhos" (Eventos).
- *Framework:* Comunica "Acabei de dar um passo" (`OnFootstep`) ou "Acabei de disparar" (`OnShoot`).
- *Seu Jogo:* Um script anexado ao jogador escuta esses eventos e decide qual som tocar, levando em conta o tipo de superfície que foi pisada ou o eco do ambiente atual.

---

## 🚫 5. Diálogos, Cutscenes e Quests
**A Framework NÃO PODE:**
- Conter árvores de diálogo ou lógica narrativa.
- Tentar gerenciar o fluxo da história, objetivos e missões do jogo.

**Por quê?**
A narrativa dita o fluxo do jogo, e a Framework deve focar puramente em mecânicas sistêmicas.

**Como funciona então?**
A Framework fornece **APIs de Controle** para o seu jogo manipular.
- *Seu Jogo:* Quando uma animação for começar, seu sistema de cutscene chama `PlayerManager.Locomotion.DisableInput()`. A framework retira o controle das mãos do jogador, a cena prossegue, e no final seu código chama `EnableInput()` para devolver o controle.

---

## 🚫 6. Progressão de RPG (XP, Skill Trees, Levels)
**A Framework NÃO PODE:**
- Conter variáveis de `Level`, `Experience` ou atributos base (como `Agility` ou `Strength`).

**Por quê?**
Jogos mais tradicionais de Survival Horror e Ação Tática frequentemente não utilizam XP. A Framework garante que o combate funcione baseado em **Dano Físico Bruto e Impacto**. 

**Como funciona então?**
Se você quiser transformar seu jogo em um RPG, crie um script próprio (ex: `PlayerRPGStats.cs`). Quando o jogador subir de nível na sua interface, este script acessa a Framework para injetar os bônus. Exemplo: `PlayerManager.Combat.SetDamageMultiplier(1.5f)`.

---

## 🛑 O Teste de Ouro (KISS & YAGNI)
Antes de escrever qualquer código dentro das pastas da NakeDev Framework, faça a si mesmo esta pergunta:
> *"Isso afeta o visual, o som ou define uma regra de negócio específica do MEU jogo em particular?"*

Se a resposta for **SIM**, não programe essa lógica na Framework. Crie um Evento/Action e desenvolva esse recurso na raiz do seu projeto (`Assets/`). Lembre-se sempre: A Framework é o **Motor** seguro e eficiente; o seu jogo é a **Lataria** única que envolve tudo.
